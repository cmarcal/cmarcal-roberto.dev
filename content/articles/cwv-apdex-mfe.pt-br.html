Core Web Vitals mostram como a página pareceu para o usuário. Apdex mostra como as chamadas por trás dela se comportaram. Olhar os dois juntos dá a melhor visão da saúde da performance.

O usuário não precisa saber onde está o gargalo. O time precisa, porque a correção depende de onde ele está: na CDN, no host, no micro frontend ou na API. Neste texto, duas métricas, Core Web Vitals e Apdex, e três ferramentas, Sentry, Grafana Faro e Prometheus, ajudam a achar esse ponto. O exemplo é um micro frontend (MFE) em React, renderizado no client side e integrado por Module Federation a um host Next.js com SSR, tudo na AWS.

1. Introdução

O cenário

O sistema tem duas aplicações que o usuário enxerga como uma página só:

  • O host é um app Next.js que renderiza no servidor (SSR). Ele é dono do shell da página, das rotas e do primeiro HTML.
  • O MFE é um app React que roda no client side: o HTML é montado no browser, não no servidor. O host carrega o MFE em runtime via Module Federation, então ele sai como um conjunto próprio de arquivos e tem deploy independente.
  • A AWS sustenta os dois: uma CDN (CloudFront) na frente, arquivos estáticos no S3, o host e a API atrás de um load balancer.

As medições e as melhorias abordadas aqui acontecem no MFE. Quando o resultado depende do host, o texto aponta o que ele pode fazer para ajudar e em quais situações ele passa a ser o problema.

Numa arquitetura de micro frontends, a responsabilidade pela performance fica dividida. A página pertence ao host, mas parte do conteúdo pertence ao MFE. Sem separar os dados por responsável, fica difícil saber quem deve corrigir uma página lenta.

Core Web Vitals em um minuto

Core Web Vitals (CWV) são um conjunto de métricas do Google que mede a experiência do usuário no carregamento (LCP), na interatividade (INP) e na estabilidade visual (CLS). Cada uma tem uma meta, e uma página é considerada boa quando as três metas são atingidas no percentil 75 dos carregamentos, avaliado separadamente para mobile e desktop (web.dev: Web Vitals):

MétricaPerguntaBom
LCP, Largest Contentful PaintQuando o conteúdo principal apareceu?2,5 s ou menos
INP, Interaction to Next PaintQuão rápido a página responde a uma interação?200 ms ou menos
CLS, Cumulative Layout ShiftO conteúdo muda de lugar durante o uso da página?0,1 ou menos

O INP substituiu o First Input Delay (FID) e se tornou uma das métricas principais dos CWV em 2024. Os CWV são medidos no browser de um usuário real, então incluem a rede, o aparelho e tudo que a página carrega, seu ou não. Até as extensões instaladas no browser entram na conta, já que elas podem atrasar a renderização da página (teste com cerca de mil extensões do Chrome).

Apdex em um minuto

O Apdex transforma um monte de tempos de resposta em um número entre 0 e 1. Você escolhe um tempo-alvo T. Cada requisição cai em uma de três zonas, e a nota é a fatia ponderada (New Relic: Apdex, Prometheus: histograms e Apdex):

As zonas

  • Satisfeito: até T
  • Tolerado: acima de T, até 4T
  • Frustrado: acima de 4T, ou com falha

A nota

(satisfeitas + toleradas / 2) / total

1,00 quer dizer que toda requisição foi rápida. Uma requisição com falha pesa contra você, igual a uma muito lenta.

Experimente abaixo: são vinte requisições fixas, e o controle define o valor de T. Observe como a nota muda mesmo sem nenhuma requisição ter ficado mais rápida ou mais lenta:

É fácil inflar o Apdex subindo o T, e difícil comparar entre times que escolheram Ts diferentes. O valor dele está na tendência de um endpoint com um T que você registrou, não no número absoluto.

Por que os dois

Eles olham coisas diferentes, então falham de formas diferentes:

  • CWV descrevem a experiência no browser. Dizem que a página pareceu lenta, mas não qual requisição causou isso.
  • Apdex descreve a latência das chamadas contra uma meta. Diz que um endpoint está lento, mas não se o usuário chegou a perceber.

Um diz que dói, o outro ajuda a achar onde. Mais adiante, as quatro combinações aparecem numa tabela pequena.

2. Desenvolvimento

Três ferramentas, três recortes

As três ferramentas não fazem o mesmo trabalho. Cada uma enxerga uma fatia diferente do caminho da requisição, e esse é o motivo de ter as três. Escolha uma para ver a fatia dela:

O Sentry enxerga o lado do usuário na página, o Faro enxerga só o seu micro frontend, o Prometheus enxerga o endpoint que ele chama. Juntos cobrem o caminho inteiro sem ninguém medir a mesma coisa duas vezes.

É no Sentry que se leem os Core Web Vitals. O SDK de browser captura LCP, INP, CLS, FCP e TTFB de carregamentos reais e junta tudo numa nota de performance de 0 a 100, com pesos de 30% LCP, 30% INP, 15% CLS, 15% FCP e 10% TTFB (Sentry: Web Vitals).

O trecho que importa aqui vai do momento em que a infraestrutura responde (TTFB) até o momento em que o browser exibe o conteúdo. É nesse pedaço que o custo do MFE aparece: baixar arquivos, executar e desenhar o resultado.

Ressalva: o dashboard de Web Vitals do Sentry cobre carregamentos iniciais de página e interações, não navegações. Se o usuário troca de rota dentro do host sem um carregamento completo, essas trocas não entram na nota.

O Faro é o gráfico de saúde do próprio MFE. O Faro Web SDK captura web vitals (TTFB, CLS, FCP, INP, LCP, em cima do pacote web-vitals), erros, logs, sessões e traces, e cada medição vem com uma classificação good, needs improvement ou poor mais a atribuição, como o elemento do LCP (Grafana: Web vitals).

Quando é inicializado dentro do MFE, com o nome e a versão do próprio MFE, tudo que ele reporta pertence àquele micro frontend. Dá para comparar um release do MFE com o anterior sem o ruído do host.

É no Prometheus que o Apdex funciona melhor. Ele não enxerga o browser. Enxerga as requisições que chegam no seu endpoint principal, e um histograma de latência ali é exatamente o que o Apdex precisa, com a meta e o limite tolerado lidos direto dos buckets (Prometheus: histograms e summaries).

Aqui está a comunicação entre o endpoint e o frontend: quantas chamadas foram rápidas, quantas lentas, quantas falharam.

O que o Prometheus mede é a latência que o servidor viu. Ela não inclui a rede do usuário. Quando uma chamada parece boa no Prometheus e lenta no Sentry ou no Faro, a diferença está na rede, na CDN ou no browser.

SentryFaroPrometheus
EnxergaA página como o usuário viveSó o MFEA API que o MFE chama
Melhor emCore Web Vitals, da resposta ao renderSaúde do MFE por releaseApdex e latência do endpoint principal
PerguntaA página parece rápida?Este micro frontend está saudável?O backend está respondendo a tempo?
Não vêQual chamada de API foi lenta, sem tracingO host e tudo fora do MFEA rede e a renderização no client

Nenhuma delas é a vencedora. Para um primeiro passo, o Sentry é o começo natural, porque a página é o que o usuário e o Google julgam. As outras duas respondem a pergunta que vem depois.

Ligando tudo

Cada ferramenta pede pouco código. O que importa é onde ele mora e como você nomeia as coisas.

Sentry vai na entrada do app. A integração de tracing é o que captura os vitals do carregamento, e o tracePropagationTargets liga a requisição do frontend ao span do backend (Sentry: tracing no React):

import * as Sentry from "@sentry/react";

Sentry.init({
  dsn: "https://<key>@o<orgId>.ingest.sentry.io/<projectId>",
  integrations: [Sentry.browserTracingIntegration()],
  tracesSampleRate: 0.2,                       // 1.0 nos testes, menos em produção
  tracePropagationTargets: [/^https:\/\/api\.example\.com/],
});

Com um MFE, vale adicionar uma tag como mfe: "checkout" e a versão do release nos eventos do Sentry, para filtrar uma nota ruim por dono. O Sentry reporta a página, e a página tem mais de um dono.

Faro é inicializado dentro do MFE, com nome e versão próprios. É isso que faz dele um recorte do MFE (Faro Web SDK):

import { initializeFaro, getWebInstrumentations } from "@grafana/faro-web-sdk";

initializeFaro({
  url: "https://collector.example.com/collect",
  app: { name: "checkout-mfe", version: "1.4.2" },
  instrumentations: [...getWebInstrumentations()],   // inclui Web Vitals
});

Combine com o time do host quem inicializa o quê. Se o host e o MFE chamarem o inicializador na mesma página, o ideal é ter dois apps com nomes claros, não um só confuso.

Prometheus precisa de um histograma de latência na API, com buckets exatamente no seu T e no 4T. A documentação é explícita: tem que haver buckets nas fronteiras exatas, e uma escolha comum é um limite tolerado de cerca de quatro vezes a meta. Com T = 0,3 s e 4T = 1,2 s:

# Apdex em 5 minutos. Os buckets são cumulativos, então as satisfeitas contam
# duas vezes e as toleradas uma, por isso a divisão por 2. Requisições com
# falha ficam só no denominador, ou seja, contam como frustradas.
(
    sum(rate(http_request_duration_seconds_bucket{le="0.3", status!~"5.."}[5m]))
  + sum(rate(http_request_duration_seconds_bucket{le="1.2", status!~"5.."}[5m]))
) / 2
/ sum(rate(http_request_duration_seconds_count[5m]))

O exemplo da própria documentação do Prometheus não exclui as requisições com falha, e ela avisa que um Apdex rigorosamente correto precisa excluir. O filtro de status acima é um jeito de fazer isso. Os nomes da métrica e do label você ajusta para a sua instrumentação.

O que puxa os números para baixo

Estes são os problemas para procurar primeiro nesse tipo de sistema, cada um com causa e correção. Toque em um item para ver a causa, a correção e onde se corrige:

  • Etapas encadeadas antes da primeira renderizaçãoLCP
    HTML, depois o JavaScript do host, depois o remoteEntry do MFE, depois os chunks, depois os dados, depois o render. Cada passo espera o anterior.
    Comece o remote mais cedo: faça preload do entry no <head> do host ou com o runtime do Module Federation, que tem preloading na versão 2 (Module Federation). Mantenha pequeno o número de chunks no caminho crítico.
    Host + MFE
  • Requisição só depois de o componente montarLCPApdex
    O MFE monta e só então pede à API o que precisa para renderizar. A chamada mais lenta define o LCP.
    Dispare a requisição quando o remote carrega, não quando o componente monta. Junte o que a primeira tela precisa numa chamada só do BFF, em vez de várias em sequência.
    MFE
  • O arquivo de entrada está com cache erradoLCP
    Um TTL longo no remoteEntry.js serve versões antigas. Sem cache, toda visita precisa buscar o arquivo de novo na origem.
    max-age curto com stale-while-revalidate no entry, cache longo e immutable nos chunks com hash de conteúdo, definidos na cache policy do CloudFront ou nos metadados do S3 (CloudFront: expiração). Mantenha os chunks antigos por um tempo, senão usuários na versão anterior tomam 404 (notas do Open edX).
    Infra (CloudFront, S3)
  • A mesma biblioteca baixada duas vezesLCPINP
    O React vem no host e de novo no MFE.
    Compartilhe as dependências comuns como singletons na config do federation. Compartilhar reduz o download em runtime, e a estratégia de share troca versões estritas por velocidade (Rspack: plugin de Module Federation).
    Host + MFE
  • O elemento do LCP aparece tardeLCP
    Uma imagem principal que só existe depois que o MFE roda, ou marcada como lazy.
    Deixe o recurso do LCP descobrível cedo, dê a ele fetchpriority alto e nunca use lazy-load nele (web.dev: otimizar o LCP). A atribuição do Faro diz qual é o elemento.
    MFE + Host
  • Primeiro byte lentoLCP
    Sem cache de CDN na frente, redirecionamentos, origem longe dos usuários.
    Coloque o CloudFront na frente do host e dos assets, evite redirecionamentos e parâmetros que quebram cache. Esse é, na maior parte, do host.
    Host + Infra
  • Um slot vazioCLS
    O HTML do servidor tem um buraco onde o MFE vai montar, então tudo abaixo pula quando ele chega.
    Reserve o espaço: um min-height ou aspect ratio no slot, e um skeleton com o tamanho final até o MFE ser renderizado.
    Host
  • Conteúdo tardio sem tamanhoCLS
    Imagens sem dimensões, web fonts que trocam, banners injetados depois do load.
    Defina width e height, faça preload da fonte principal e escolha uma fallback com métricas parecidas.
    MFE
  • Um render pesado depois de uma interaçãoINP
    Listas grandes e estado guardado bem acima dos componentes que o usam, então um clique re-renderiza metade da tela.
    Aproxime o estado dos componentes que o usam, virtualize listas longas e marque atualizações não urgentes com useTransition.
    MFE
  • Main thread ocupadaINP
    Bundles grandes, scripts de terceiros e long tasks que atrasam a próxima atualização da tela.
    Carregue features raras com React.lazy, adie scripts de terceiros e quebre handlers longos em passos menores.
    MFE + Host
  • Hidratação pesada no hostLCPINP
    O host hidrata a página inteira antes de o MFE sequer começar a carregar. A main thread fica ocupada, o remote espera e as primeiras interações demoram a responder.
    Envie menos JavaScript de client no host: mantenha o que for possível em Server Components e carregue sob demanda os Client Components fora da dobra (Next.js: lazy loading). Comece a carregar o remote sem esperar a hidratação terminar.
    Host
  • Um frontend tagarelaApdex
    Várias chamadas em sequência para montar uma tela, cada uma pagando a própria latência.
    Um endpoint por view no BFF, chamadas em paralelo e um histograma por rota para ver qual rota puxa a nota para baixo.
    MFE + API / BFF
  • Trabalho lento atrás do endpointApdex
    Queries N+1, sem cache para respostas de muita leitura, capacidade fria ou subdimensionada.
    Corrija a query, faça cache das leituras e defina capacidade mínima e escala por latência para o serviço atrás do load balancer.
    API + Infra
  • Erros lidos como frustraçãoApdex
    Uma dependência falhando conta exatamente como uma lenta.
    Olhe primeiro a taxa de erro, depois a latência. Adicione timeouts e retries onde for seguro.
    API
  • Um número que ninguém escolheuApdex
    Um T para todas as rotas, ou buckets que não batem com T e 4T, então a query não consegue calcular.
    Escolha o T por tipo de rota, registre e faça os buckets do histograma baterem.
    Monitoramento

O host: o que ele pode fazer e quando é o problema

Alguns dos números acima são decididos fora do MFE. O host renderiza no servidor, mas o MFE só existe no browser, e esse vão molda a página (o Next.js também deixa um client component pular a renderização no servidor com ssr: false, veja Next.js: lazy loading).

O que o host pode fazer pelo MFE

  • Reservar o slot do MFE no HTML do servidor, com um skeleton do tamanho certo. Isso tira um layout shift e dá ao browser algo para exibir.
  • Fazer preload do arquivo de entrada do MFE no <head>, para o carregamento do MFE começar no primeiro byte e não depois da hidratação.
  • Colocar o shell da página na primeira resposta e manter o servidor rápido, para o TTFB não comer o orçamento do LCP.
  • Ser dono das dependências compartilhadas, para existir um React só.

Quando o host é o problema

  • O TTFB está alto. O Sentry mostra primeiro byte lento em páginas com e sem o MFE. O MFE não resolve isso.
  • O elemento do LCP não é do MFE. A atribuição do Faro aponta para um elemento do host, como um banner ou a imagem do header.
  • O INP é ruim longe do MFE. Os scripts do próprio host e de terceiros mantêm a main thread ocupada.
  • A hidratação é pesada. O host hidrata muita coisa antes de o MFE sequer começar a carregar.

O que decide de quem é um número ruim é a atribuição, não a opinião. O elemento do LCP e o detalhamento de tempos dizem se o tempo foi para o primeiro byte, para descobrir o recurso, para baixar ou para renderizar (web.dev). Só então o ticket vai para o backlog de alguém.

Saudável. Fique de olho na tendência por release e na fatia de 25% dos usuários que o percentil 75 esconde.

O problema está no client ou no caminho até ele. A API responde a tempo, mas a página está lenta. Olhe a sequência de carregamento, o tamanho do bundle, os headers de cache, o slot vazio e o TTFB do host.

A página esconde um backend lento. Skeletons, caches ou conteúdo acima da dobra estão mascarando chamadas lentas, ou os endpoints lentos ainda não estão no caminho crítico. Vai aparecer no INP ou na próxima feature que precisar desses dados.

Comece pelo backend. Chamadas lentas ou com falha são a causa mais provável da página ruim. Corrija o endpoint primeiro e meça os vitals de novo antes de mexer no frontend.

O segundo caso é o menos intuitivo. Um CWV bom não prova que o backend está saudável, porque um bom front end consegue esconder o problema por um tempo.

3. Conclusão

Para esse tipo de sistema, o trabalho se divide assim:

FerramentaMétricaRecortePergunta que responde
SentryCore Web VitalsDa resposta da infraestrutura ao render no browserA página parece rápida para usuários reais?
Grafana FaroVitals, erros, tracesSó o MFE, por releaseO micro frontend está saudável?
PrometheusApdexO endpoint principal que o frontend chamaAs chamadas estão respondendo a tempo?

Se quiser testar sem montar tudo de uma vez, comece pequeno e nesta ordem:

  1. Comece pela página. Ligue o tracing do Sentry e olhe LCP e TTFB das páginas que carregam o MFE. Pegue uma linha de base antes de mudar qualquer coisa.
  2. Um nome para o MFE. Inicialize o Faro dentro dele, com nome e versão próprios, para o próximo release ter com o que ser comparado.
  3. Um Apdex que você registrou. Escolha o T do endpoint principal, adicione os buckets correspondentes e monte um gráfico da query.

Uma nota boa não é o objetivo, o objetivo é chegar mais perto do problema. CWV dizem que a página dói, o Apdex ajuda a achar a chamada e a atribuição diz de quem é. Leia os dois juntos, mude uma coisa, meça de novo.
