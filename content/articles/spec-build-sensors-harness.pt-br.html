Turborepo, React, Fastify e um pacote shared, com um agente fazendo boa parte da digitação

Como organizo um monorepo TypeScript para que agentes de IA entreguem mudanças previsíveis, fáceis de revisar e prontas para o merge.

Um agente escreve uma feature em minutos. O difícil é confiar no que ele devolve. Parei de tentar resolver isso lendo cada diff com mais atenção e passei a organizar o projeto em três etapas: o Spec decide o que construir, o Build produz em isolamento e os Sensors provam que dá para fazer o merge. Neste artigo mostro essa estrutura num projeto pessoal pequeno, o FutMeet. Ele ainda está em construção e não foi lançado, então o repositório continua mudando enquanto escrevo isto.

Etapa 1

Spec

Explorar a ideia, escrever, planejar. Ainda sem código.

Etapa 2

Build

Branch isolada, regras escritas, testes junto com o código.

Etapa 3

Sensors

Checagens automáticas que passam ou falham. Falhou, corrige e roda de novo.

1. Introdução

IA na vida real

No meu dia a dia, um agente de IA já escreve boa parte do código. No FutMeet, o README diz exatamente isso: agentes escrevem a maioria das mudanças. Não é papo de futuro, é como uso esse repositório hoje.

A velocidade é real, mas o problema não é ela. O agente esquece uma regra que você explicou ontem. Instala uma dependência que ninguém pediu. Diz que terminou com um teste quebrando. Desenvolvedores também fazem isso, só que o agente erra mais rápido e não cansa.

Ler cada diff com mais cuidado não escala, e você vira o gargalo. Prefiro gastar esse esforço uma vez, na estrutura do projeto.

O que é um harness

O termo vem do mundo dos agentes. Birgitta Böckeler, no martinfowler.com, define como tudo num agente de IA, exceto o modelo em si (no original: everything in an AI agent except the model itself), e foca na parte que você monta para o seu projeto: o outer harness (Harness engineering for coding agent users, abril de 2026). A OpenAI usou a mesma palavra no relato de como construiu um produto com o Codex.

Böckeler divide o harness em dois tipos de controle:

Guides (feedforward)

Conduzem o agente antes de ele agir, para a primeira tentativa ter mais chance de acertar. Exemplos: regras no estilo AGENTS.md, skills, code mods.

Sensors (feedback)

Observam depois que o agente agiu e deixam ele se autocorrigir. Exemplos: testes, linters, type checkers, um reviewer de IA.

Ela também separa controles computacionais (determinísticos e rápidos, como um type checker) dos inferenciais (julgamento semântico, como um code review de IA, mais lento e menos previsível). E o seu trabalho passa a ser ajustar o harness: se o mesmo erro aparece duas vezes, você melhora um guide ou um sensor, em vez de supervisionar mais de perto.

As três etapas

As minhas três etapas não são termos da Böckeler. É só o jeito que encontrei de organizar a mesma ideia dentro do repositório:

  • Spec é um guide. O agente esclarece a intenção, compara abordagens e escreve spec e plano antes de encostar no código.
  • Build também é um guide. O trabalho acontece num worktree isolado, e regras escritas (skills) dizem ao agente como este projeto faz as coisas.
  • Sensors são o feedback. Checagens automáticas decidem se o resultado pode virar pull request.

Dividir os guides em Spec e Build é escolha minha. Ajuda porque acontecem em momentos diferentes e falham de jeitos diferentes: uma spec ruim constrói a coisa errada do jeito certo, um build ruim implementa a coisa certa do jeito errado.

Este é o ciclo inteiro. Clique pelos passos ou aperte Play.

Por que estruturar assim

  • As regras moram no repositório. Uma nova sessão do agente, uma pessoa nova no time ou outra ferramenta leem os mesmos arquivos. Nada depende de alguém lembrar de repetir.
  • Errar cedo sai barato. Uma spec errada custa um parágrafo. Uma branch errada custa um worktree que você apaga. Um sensor falhando custa uma nova rodada. Um bug em produção custa muito mais.
  • O review encolhe. Quando o pull request existe, as perguntas mecânicas já foram respondidas. Aí você revisa a ideia e o design, que é o que só você consegue julgar.

2. Desenvolvimento

O monorepo

O FutMeet ajuda quem joga bola casualmente a organizar o futebol: alguém abre uma sala e compartilha o link, o pessoal entra, e o app sorteia times equilibrados. É um monorepo TypeScript em npm workspaces, orquestrado pelo Turborepo:

  • apps/web: React 19 e Vite, uma single-page app.
  • apps/api: o BFF, uma API REST em Fastify 5 com PostgreSQL.
  • packages/shared: tipos de domínio e utils que os dois apps importam.
  • packages/sensors: o código por trás do npm run verify.
  • packages/tsconfig e packages/oxlint-config: uma configuração de TypeScript e uma de lint para todo mundo.

O Turbo define a ordem das tasks: o shared builda primeiro e os apps depois.

// turbo.json
{
  "tasks": {
    "build":     { "dependsOn": ["^build"], "outputs": ["dist/**"] },
    "typecheck": { "dependsOn": ["^build"] },
    "dev":       { "cache": false, "persistent": true },
    "lint": {},
    "test": {}
  }
}

^build quer dizer "builde minhas dependências antes" (docs do Turborepo). Como o @futmeet/shared exporta os arquivos compilados de dist/, o typecheck do web e da API usa o shared já compilado.

O pacote shared é o contrato entre front e back. Uma única definição, importada por alias e nunca por caminho relativo entre pacotes:

// packages/shared/src/types/index.ts
// 'sorting' is frontend-only transient state; backend only stores 'setup' | 'complete'
export type GameStatus = 'setup' | 'sorting' | 'complete';
export type ServerGameStatus = 'setup' | 'complete';

// apps/web e apps/api
import type { Game } from '@futmeet/shared/types';

Se a API muda o formato de um Game, o typecheck do web deve falhar na mesma rodada. Não medi quantas vezes isso me salva. O que sei é que parei de ver esse tipo de erro no review.

Escolha uma etapa para ver quais arquivos do repositório pertencem a ela:

  • CLAUDE.mdWorkflow obrigatório, índice de skills e regras do projeto
  • Issue ou ticketSpec e plano de cada mudança. Fora do repositório
  • adr/Decisões difíceis de reverter
  • .claude/skills/Uma pasta por skill, detalhes em references/
  • .githooks/Sem commit na main nem no checkout principal
  • apps/web, apps/apiO código que o agente muda
  • packages/sharedContrato entre front e back
  • packages/tsconfig, oxlint-configUma configuração, aplicada em tudo
  • turbo.jsonOrdem das tasks e cache
  • packages/sensors/verify, lint de skills, presença de testes, budget do bundle
  • .claude/settings.jsonHook que bloqueia o gh pr create se algum sensor falhar
  • .github/workflows/ci.ymlOs mesmos sensors, como segunda barreira

Spec: decida antes de digitar

A primeira etapa tem uma regra: nada de código antes de a ideia estar escrita. Primeiro o agente pergunta o que você quer e compara as opções. Disso saem uma spec e um plano enxutos, com o objetivo principal e os passos, que ficam no ticket: uma issue do GitHub, um card do Jira ou qualquer outra ferramenta de gestão. Se a decisão for difícil de reverter, vira também um ADR, e esse fica no repositório.

Um exemplo do FutMeet, resumido. A spec para adicionar Docker à API começa com o objetivo e os arquivos que vai tocar:

# Docker Configuration Design: FutMeet API

**Scope:** `apps/api`

## Goal
Add Docker support to the API with two modes:
- `dev` profile: starts only the PostgreSQL database.
- `deploy` profile: starts the database, runs migrations,
  then starts the compiled API.

## Files
apps/api/
  Dockerfile          (new: multi-stage build)
  docker-compose.yml  (updated: profiles, migrate service, api service)
  .env.example        (updated)

O que faz disso um guide, e não só documentação, são duas coisas. Ela declara o escopo, então o agente tem um limite. E é curta o bastante para uma pessoa ler em um minuto, então dá para discordar antes de quarenta arquivos mudarem.

O formato e o hábito vêm do Superpowers, uma metodologia feita de skills que se combinam: ele pergunta o que você quer, mostra a spec em partes curtas para você aprovar e só então monta o plano, antes de qualquer código (README). Por padrão ele escreve tudo em arquivos, então o FutMeet guarda esses arquivos em docs/superpowers/.

Prefiro não commitar spec e plano. O time já conversa sobre o trabalho no ticket, e ele não fica ocupando espaço no repositório depois do merge. A spec também é onde você pega os erros caros: corrigir um parágrafo é a edição mais barata que você vai fazer na semana.

Build: isole e escreva as regras

A segunda etapa responde duas perguntas: onde o trabalho acontece e como o agente descobre as regras do projeto.

Onde. Sempre num worktree próprio, nunca na main. Isso está nas regras do projeto e, se alguém tentar commitar na main, um hook barra:

git worktree add .worktrees/feat-room-link -b feat/room-link

# .githooks/pre-commit
Direct commits to 'main' are blocked. Create a worktree: git worktree add ...
Commits from the primary checkout are blocked. Work in a worktree ...

Como. As regras do projeto ficam em .claude/skills/. Cada skill é um SKILL.md curto, de no máximo 100 linhas, que aponta para uma pasta references/ com o detalhe. O CLAUDE.md guarda só o índice, então o agente carrega a única skill que combina com a tarefa e mais nada:

Trabalhando emSkill que o agente carrega
Qualquer mudança, branch, limpezaworktree-workflow
Novo módulo da API, rotasapi-fastify-module
Componentes e CSS Modulescomponent-architecture-css-modules
Formuláriosforms-react-hook-form-zod
Testestesting-vitest
Antes de abrir um PRpr-gate

Algumas regras não cabem em config, então ficam escritas em texto. A API segue Route → Controller → Service → Repository → Query e os services não têm try/catch. O web usa CSS Modules e não aceita estilo inline. O código compartilhado entra por alias. Um agente que lê isso antes de mexer em apps/api para de reinventar as camadas a cada tarefa.

Manter cada skill abaixo de 100 linhas é um limite que escolhi de propósito. Instrução longa é lida com menos cuidado, por agentes e por pessoas. O limite também vira um sensor, como você vai ver a seguir.

Testes fazem parte do Build, não ficam para depois: todo arquivo que o agente cria ou modifica vai com seus testes no mesmo commit.

Sensors: deixe as checagens decidirem

Um sensor é uma checagem automática que passa ou falha, sem meio-termo. O npm run verify roda todos, e um pull request só abre quando todos passam:

SensorO que pega
lint, typecheckWarnings do oxlint, erros de tipo
format:checkArquivos alterados fora do padrão do Prettier
knipArquivos, dependências e binários sem uso
skills:lintSkills com mais de 100 linhas, links quebrados em references/, skills fora do índice
test:presenceArquivo de código alterado sem teste, componente web alterado sem teste de a11y
secrets, audit:prodCredenciais commitadas, vulnerabilidades altas ou críticas
testTestes falhando, cobertura abaixo do piso
build, bundleErros de compilação, bundle do web acima do budget em gzip
db:checkMigrations que não aplicam ou não revertem (sempre no CI)

Todos esses são computacionais no sentido da Böckeler: determinísticos e rápidos o bastante para rodar a cada mudança. O FutMeet também tem um inferencial, a skill security-pr-review, mas ela é um reviewer, não um portão.

Repare que alguns sensors checam o próprio harness: o skills:lint mantém os guides do Build em ordem, e o test:presence faz "todo arquivo vai com teste" deixar de ser desejo e virar regra. É o ciclo que a Böckeler descreve: quando um erro se repete, você transforma o guide em sensor.

O runner é um script pequeno. Roda cada sensor, imprime um resumo e sai com código diferente de zero se algum falhar:

// packages/sensors/src/verify.mjs
export const SENSORS = ['lint', 'typecheck', 'format:check', 'knip', 'skills:lint',
  'test:presence', 'secrets', 'audit:prod', 'test', 'build', 'bundle'];

// verify failed: test:presence red. Fix the cause, then rerun npm run verify.
// verify passed: all sensors green.

Teste você mesmo. O agente mudou um arquivo e esqueceu o teste, então a primeira rodada vai falhar. Escreva o teste que falta e rode de novo, ou tente pular o teste e veja o que acontece.

  1. lint
  2. typecheck
  3. format:check
  4. knip
  5. skills:lint
  6. test:presence
  7. secrets
  8. audit:prod
  9. test
  10. build
  11. bundle

Esse último botão mostra a regra mais importante do pr-gate. O pr-gate diz que a correção precisa mudar código, testes ou config para o sensor passar pelo motivo certo. Pular testes, baixar o piso de cobertura, subir o limite do bundle, adicionar comentário de lint-disable ou @ts-ignore não conta. Sem essa regra, o agente faz tudo passar do jeito mais fácil.

O bloqueio acontece em três lugares, do mais perto do agente ao mais longe:

  1. Um hook do Claude Code em .claude/settings.json roda antes de todo gh pr create e bloqueia o comando enquanto algum sensor estiver falhando.
  2. Git hooks em .githooks/ bloqueiam commits na main e no checkout principal.
  3. O CI roda os mesmos sensors em todo pull request, então nada depende da máquina local.

Sensor só pega o erro que alguém lembrou de checar. Os meus sensors não dizem se a feature é uma boa ideia nem se o código é fácil de ler. Isso fica com a spec e com o review. Por isso digo que o código está pronto para o merge, não que está seguro.

Outros harnesses que valem a leitura

O FutMeet é um projeto pequeno. Estes dois são mais conhecidos e mostram escolhas diferentes:

Superpowers

Uma metodologia completa entregue como skills: pergunta primeiro, escreve spec, depois plano, depois executa tarefa por tarefa com subagents e review. Começa a funcionar desde a primeira mensagem, porque as skills disparam sozinhas (README). Uso o Superpowers na etapa de Spec do FutMeet.

Skills do Matt Pocock

Skills pequenas e fáceis de combinar para "engenharia de verdade, não vibe coding". Diferente de frameworks que tomam conta do processo todo, elas deixam você adaptar só o que precisar (README).

O padrão que levo dos dois: skills são o jeito mais barato de transformar uma regra do projeto em guide. O que elas não dão é o feedback de passou ou falhou. Essa é a parte que acrescentei em packages/sensors.

3. Conclusão

Um agente é rápido, mas esquecido. O harness faz o projeto lembrar no lugar dele. Juntas, as três etapas ficam assim:

EtapaTipo de controlePergunta que respondeNo FutMeet
SpecGuide (feedforward)O que estamos construindo e por que deste jeito?Spec e plano antes do código, ADRs no repositório
BuildGuide (feedforward)Onde o trabalho acontece e como este projeto faz as coisas?Worktrees, git hooks, skills, testes junto com o código
SensorsFeedbackDá para fazer o merge?npm run verify, o hook de PR, o CI

O monorepo também ajuda. Com web, API e contrato compartilhado no mesmo lugar, sobra um conjunto de skills, um verify e um grafo de tasks que o Turbo mantém em ordem. Com vários repositórios, eu teria que manter vários harnesses em sincronia.

Se quiser testar sem reconstruir nada, comece pequeno e nesta ordem:

  1. Um sensor. Faça um único comando que rode lint, tipos, testes e build, e devolva código diferente de zero em qualquer falha.
  2. Uma regra que o agente quebra. Escreva como uma skill curta ou uma seção do seu arquivo de instruções. Quando ele quebrar de novo, transforme em checagem.
  3. Um hábito antes do código. Peça uma spec curta e leia antes de o agente começar.

O harness nunca fica pronto. Sempre que o agente fizer algo inesperado, pergunte qual guide teria evitado ou qual sensor teria pegado, e adicione esse. Com o tempo, você revisa menos código e mais ideia.
